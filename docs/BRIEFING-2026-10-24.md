## 2. What you need to understand for calls

| Term | Meaning and common mistake |
|---|---|
| Logical qubit | An error-corrected computational resource. Not the same as a physical device qubit; counts may omit idle patches, factories or routing. |
| Physical qubit | Hardware resource under a particular error-correction architecture, noise model, runtime and error target. A logical-width reduction does not scale every physical component equally. |
| Toffoli vs T | Different quantum gates/cost units. Counts cannot be converted by one universal multiplier when AND gadgets and measurement-based uncomputation are mixed. |
| Subroutine vs full attack | Point addition is one component of an elliptic-curve discrete-log attack. A better component does not by itself establish a smaller or faster complete machine. |
| Operating point | One coherent design choice: e.g. low-width vs low-gate, one-hour vs one-day deadline, or one key vs amortized many-key execution. Never combine the best width from one row with the best gate count from another. |
| Classical vs coherent addend | A circuit with a classically supplied point has a different interface from a coherent lookup-selected point. The latter can require extra lookup/unlookup costs. |
| Bound vs observation | An upper bound is not a measured actual cost. A lower observed value versus an upper bound is not proof of dominance over an unpublished implementation. |
| Failure evidence | Passing a sampled test set is not universal correctness. Input distribution, nonce selection, sample independence and retry cost matter. |
| Provenance vs truth | A number appearing in a source proves literal attribution only. It does not prove the number has the claimed unit, row, scope or scientific validity. |

**Thirty-second project explanation:** “Quantum threat headlines mix logical qubits, physical machines and individual circuit steps. We are testing a small evidence workbench that shows the exact source and assumptions behind two claims, then explains when the comparison is unsupported. AI drafts the fields; deterministic checks and human review keep the evidence inspectable. We do not generate attack circuits or predict Q-Day.”

**Questions for an analyst call:** What was your last difficult comparison? Which two artifacts did you read? Which assumption took longest to resolve? Would a quote-backed card/export enter your next article or risk memo? What would make you distrust it? Ask for the actual next artifact, not general enthusiasm. [Unsent outreach drafts](build/OUTREACH.md).

## 3. Why useful—and why it may not be

Observed workflow: [Marin Ivezic](https://postquantum.com/security-pqc/ecdsa-fail-low-qubit-circuit/) manually separates logical width, point-addition inputs and full-machine assumptions; [Samuel Jaques](https://sam-jaques.appspot.com/quantum_landscape) wants a more precise taxonomy of physical assumptions. These are potential users and existing solutions, not customers.

[INFERENCE] Value hypothesis: faster, auditable preparation of an analyst's explanation or correction, with exportable evidence and visible unknowns. Possible later buyers are specialist advisory firms and in-house risk teams; no budget, price, time saving or willingness to pay is established. A collaboration/feed for the existing tracker may be more useful than a new destination site.

Failure conditions: the existing CSV plus expert prose already suffice; manual semantic review costs more than it saves; new papers do not fit the schema; users need an independently validated physical estimate rather than provenance. If those occur, do not add a chatbot and call the market validated.

Full source dates/read depths: [practitioner pain](research/practitioner-pain.md), [competitors/users](research/build/competitors-users.md), [market story](research/build/market-story.md). The new practitioner report supersedes older “unserved ledger” assumptions.

## 4. What we propose to build

Authoritative contract: [PRODUCT](build/PRODUCT.md), [ARCHITECTURE](build/ARCHITECTURE.md), [PLAN](build/PLAN.md). GitHub implementation tickets are preparation, not completed work.

1. Six reviewed operating-point records: EF-893; Google point-addition low-qubit and low-gate; Litinski single-key and amortized k=11; one Gidney full-attack physical estimate. Each metric has a unit/layer, statistic/bound and evidence location. Unknowns stay unknown.
2. Card and two-card comparison pages: source/version/quote visible; explicit scope and assumptions; `comparable`, `caveat`, `not_comparable` or `insufficient_evidence`. No misleading ratio when definitions differ.
3. An allowlisted-text CLI extraction run producing a **list of draft cards**, strict canonical span/token checks, human review/export and a read-only run page. No arbitrary PDF execution, background news agent or writable approval database.
4. Small transparent evaluation: three development and three independently human-labelled held-back comparisons; extraction mapping errors/false accepts/false rejects; individual failures and n. Same-model **same-source-access** JSON baseline if a funded API key exists. These tiny samples do not establish general accuracy.
5. Early deployment and a ≤2-minute video of the actual surface. Optional auth, memory and headline parsing only after the complete core works; no partner badges for unused integrations.

**What exists now:** research, specifications, tickets, source-candidate corpus, audits and a runnable backup probe. **What does not:** the Ledger application, reviewed seed JSON, actual extraction/eval results, live URL, finished video or Devpost submission. Commands such as `make verify` in the build contract are future acceptance interfaces, not currently available tools.
